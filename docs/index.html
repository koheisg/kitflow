GoユーザーとAIエージェント向け GitFlow-style CLI

kitflow

GitFlowの定番操作を、小さなGo製CLIで安全に実行するためのツールです。feature / release / hotfix の作成、完了、公開、追跡をシンプルなコマンドで扱えます。

GitHubを見る ユースケースを見る Skillの使い方

Install

With Homebrew:

brew tap koheisg/tap
brew trust --formula koheisg/tap/kitflow
brew install kitflow

With Go:

go install github.com/koheisg/kitflow@latest

Or build from source:

git clone https://github.com/koheisg/kitflow.git
cd kitflow
go build -o kitflow .

Quick start

kitflow init
kitflow feature start login
# edit, test, commit
kitflow feature finish login
kitflow release start 1.0.0
# final checks
kitflow release finish 1.0.0

Commands that change branches require a clean working tree so unrelated local changes are not accidentally carried into merges.

Command reference

GoalCommandResult
Initializekitflow initStores local Git config and creates develop when possible.
Start a featurekitflow feature start <name> [<base>]Creates feature/<name> from develop or the supplied base branch.
Finish a featurekitflow feature finish [name]Merges into develop with --no-ff and deletes the local feature branch.
Start a releasekitflow release start <version> [<base>]Creates release/<version> from develop or the supplied base branch.
Finish a releasekitflow release finish <version>Merges into main and develop, creates an annotated tag, then deletes the release branch.
Start a hotfixkitflow hotfix start <version> [<base>]Creates hotfix/<version> from main or the supplied base branch.
Finish a hotfixkitflow hotfix finish <version>Merges into main and develop, creates an annotated tag, then deletes the hotfix branch.
Publish a branchkitflow feature publish [name]Pushes the branch to the configured remote and sets upstream tracking. Release and hotfix publish commands work the same way.
Track a remote branchkitflow feature track <name>Creates a local tracking branch from the configured remote. Release tracking works the same way.
Check statekitflow statusPrints main/develop branch names, prefixes, and the current branch.

Practical use cases

1. Develop a new feature safely

Keep ordinary product work such as login, search, or notifications isolated from develop until it is ready.

kitflow feature start login
# implement login
# run tests
git add .
git commit -m "Add login feature"
kitflow feature finish login

feature/login → develop

2. Publish a feature for pull request review

Push the branch to the remote and set upstream tracking in one step.

kitflow feature start search
# commit changes
kitflow feature publish search

You can then open a pull request from feature/search to develop.

3. Take over someone else's feature branch

Create a local tracking branch from an existing remote feature branch.

git fetch origin
kitflow feature track payment

Useful for pair programming, handoffs, and support rotation.

4. Prepare a release candidate

Use a release branch for version bumps, changelog updates, documentation, QA fixes, and final verification.

kitflow release start 1.2.0
# update version, changelog, docs
git commit -m "Prepare 1.2.0 release"
kitflow release finish 1.2.0

release/1.2.0 → main + develop + tag 1.2.0

5. Patch production without unreleased changes

Start from main so unfinished work in develop does not leak into an urgent fix.

kitflow hotfix start 1.2.1
# fix production bug
git commit -m "Fix session timeout"
kitflow hotfix finish 1.2.1

hotfix/1.2.1 → main + develop + tag 1.2.1

6. Patch an older supported line

Pass an explicit base branch when maintaining multiple stable versions.

git checkout -b support/1.1 1.1.5
kitflow hotfix start 1.1.6 support/1.1

Useful for CLIs, libraries, and products with long-term support branches.

7. Share a release branch with QA

Publish a release branch so QA, documentation, and release engineering can collaborate.

kitflow release start 2.0.0
kitflow release publish 2.0.0

Another teammate can join with kitflow release track 2.0.0.

8. Audit active flow branches

List outstanding feature, release, and hotfix branches before planning a release.

kitflow feature list
kitflow release list
kitflow hotfix list
kitflow status

Helpful before release freezes, sprint reviews, and cleanup days.

9. Give AI agents a safe GitFlow playbook

The repository includes a reusable skill file for AI coding agents.

skills/kitflow/SKILL.md

It documents when to use kitflow, what safety checks to run, and how to verify branch operations.

AI agent skill guide

kitflow includes a reusable skill for AI coding agents at skills/kitflow/SKILL.md. Use it when you want an agent to operate GitFlow-style workflows with the same safety checks every time.

What the skill teaches an agent

When to use kitflow

The skill tells the agent to use kitflow for GitFlow-style tasks: initialize config, start/finish/list feature, release, or hotfix branches, publish branches, track remote branches, and check status.

Safety checks first

Before branch changes, merges, tags, deletes, or pushes, the skill instructs the agent to inspect the repository state.

git status --short
git branch --show-current
git log --oneline -5

Verification after actions

After branch-changing commands, the skill tells the agent to verify current state and upstream tracking when relevant.

kitflow status
git rev-parse --abbrev-ref HEAD@{upstream}

How to add the skill to an agent

Exact installation depends on the AI coding agent. For agents that support file-based skills, copy or reference the included skill directory:

skills/kitflow/SKILL.md

If your agent keeps skills in a global directory, copy the whole directory there:

cp -R skills/kitflow /path/to/your/agent/skills/

If your agent supports project-local skills, keep skills/kitflow/SKILL.md in the repository and tell the agent to use the kitflow skill.

Example prompts for agents

Use the kitflow skill and start a feature branch named login.
Use kitflow to finish the current feature after checking the working tree.
Use the kitflow skill to prepare release 1.4.0.
Use kitflow to publish this release branch and verify upstream tracking.
Use kitflow to create hotfix 1.4.1 from main.

Expected agent behavior

  • Check that the working tree is clean before changing branches.
  • Use kitflow --dry-run when you ask for a preview.
  • Run the matching kitflow command instead of hand-writing a sequence of Git commands.
  • Stop and ask you what to do if local changes would be affected.
  • Verify the branch, status, and upstream after the operation.

Real-world recipes

Solo development: keep main always releasable

kitflow init
kitflow feature start cli-help
# implement
git commit -am "Improve CLI help"
kitflow feature finish cli-help
kitflow release start 0.2.0
kitflow release finish 0.2.0
git push origin main develop --tags

Team development: review through pull requests

kitflow feature start oauth
# commit changes
kitflow feature publish oauth
# open PR: feature/oauth -> develop
# after review and merge policy approval
kitflow feature finish oauth

Deploy a release candidate to QA

kitflow release start 3.4.0
kitflow release publish 3.4.0
# CI deploys release/3.4.0 to QA
# after QA passes
kitflow release finish 3.4.0
git push origin main develop --tags

Never forget to bring hotfixes back to develop

kitflow hotfix start 3.4.1
# fix and test
git commit -am "Fix billing webhook retry"
kitflow hotfix finish 3.4.1
git push origin main develop --tags

hotfix finish merges into both main and develop, reducing the chance of losing the fix in future releases.

Configuration

kitflow init uses local Git config values:

git config --local kitflow.branch.main main
git config --local kitflow.branch.develop develop
git config --local kitflow.prefix.feature feature/
git config --local kitflow.prefix.release release/
git config --local kitflow.prefix.hotfix hotfix/

Change the remote name when needed:

git config --local kitflow.remote upstream

Safety notes

  • Branch-changing commands stop when the working tree is dirty.
  • Use --dry-run to preview Git write operations.
  • Use --verbose to print underlying Git commands while debugging.
  • Release and hotfix finish commands create annotated tags and fail if the tag already exists.
  • If a merge conflict happens, resolve it with normal Git conflict-resolution steps.
kitflow --dry-run release finish 1.2.0
kitflow --verbose hotfix start 1.2.1

実際の利用ユースケース

1. 新機能を安全に開発する

ログイン、検索、通知など、通常の機能追加をdevelopから分離します。

kitflow feature start login
# implement login
# run tests
git add .
git commit -m "Add login feature"
kitflow feature finish login

feature/login → develop

2. Pull Request用にfeatureを公開する

レビュー前にremoteへpushし、upstream trackingも同時に設定します。

kitflow feature start search
# commit changes
kitflow feature publish search

GitHub上でfeature/searchからdevelop向けのPRを作成できます。

3. 他人が作ったfeatureを引き継ぐ

remote branchをローカルにtracking branchとして作成します。

git fetch origin
kitflow feature track payment

ペア開発、担当交代、サポート当番で便利です。

4. リリース準備ブランチを切る

リリース前のバージョン調整、CHANGELOG更新、ドキュメント更新、最終QAをrelease/で行います。

kitflow release start 1.2.0
# update version, changelog, docs
git commit -m "Prepare 1.2.0 release"
kitflow release finish 1.2.0

release/1.2.0 → main + develop + tag 1.2.0

5. 本番障害をhotfixで即修正する

developの未リリース変更を含めず、mainから緊急修正します。

kitflow hotfix start 1.2.1
# fix production bug
git commit -m "Fix session timeout"
kitflow hotfix finish 1.2.1

hotfix/1.2.1 → main + develop + tag 1.2.1

6. 過去の安定版からパッチを作る

保守ブランチなど、標準base以外から開始したい場合は第2引数でbaseを指定します。

git checkout -b support/1.1 1.1.5
kitflow hotfix start 1.1.6 support/1.1

複数バージョンを保守するライブラリやCLIで使えます。

7. release branchをチームに共有する

QA担当やドキュメント担当が同じrelease branchへ参加できます。

kitflow release start 2.0.0
kitflow release publish 2.0.0

別メンバーはkitflow release track 2.0.0で参加できます。

8. 作業前に何が残っているか確認する

長期ブランチが増えたときに種類ごとに棚卸しします。

kitflow feature list
kitflow release list
kitflow hotfix list
kitflow status

リリース前のブランチ整理に便利です。

AIエージェント向けSkillの使い方

kitflow にはAI coding agent向けの再利用可能なskillが skills/kitflow/SKILL.md に含まれています。エージェントにGitFlow風の操作を任せる時、安全確認と実行手順を毎回そろえるために使います。

Skillがエージェントに教えること

いつkitflowを使うか

初期化、feature / release / hotfix の開始・完了・一覧、branch公開、remote branch追跡、status確認などのGitFlow風タスクでkitflowを使うよう案内します。

先に安全確認する

branch変更、merge、tag作成、branch削除、pushの前に、リポジトリ状態を確認するよう指示します。

git status --short
git branch --show-current
git log --oneline -5

操作後に検証する

branch操作後は状態確認を行い、publish / track の後はupstream trackingも確認します。

kitflow status
git rev-parse --abbrev-ref HEAD@{upstream}

Skillをエージェントに追加する方法

具体的な導入方法はAI coding agentごとに異なります。file-based skillに対応している場合は、このskillディレクトリをコピーまたは参照します。

skills/kitflow/SKILL.md

エージェントがグローバルなskillsディレクトリを持つ場合は、ディレクトリごとコピーします。

cp -R skills/kitflow /path/to/your/agent/skills/

project-local skillに対応している場合は、リポジトリ内の skills/kitflow/SKILL.md をそのまま置き、「kitflow skillを使って」と依頼します。

エージェントへの依頼例

kitflow skillを使って login feature branchを作って。
作業ツリーを確認してから、現在のfeatureをkitflowでfinishして。
kitflow skillを使って release 1.4.0 を準備して。
このrelease branchをkitflowでpublishして、upstreamも確認して。
mainから hotfix 1.4.1 をkitflowで作って。

期待するエージェントの動き

  • branchを変更する前に作業ツリーがcleanか確認する。
  • プレビューを頼まれた時は kitflow --dry-run を使う。
  • Gitコマンド列を手書きせず、該当する kitflow コマンドを使う。
  • ローカル変更に影響が出そうな場合は止まってユーザーに確認する。
  • 操作後にbranch、status、upstreamを検証する。

設定

kitflow initは以下のローカルGit configを使用します。

git config --local kitflow.branch.main main
git config --local kitflow.branch.develop develop
git config --local kitflow.prefix.feature feature/
git config --local kitflow.prefix.release release/
git config --local kitflow.prefix.hotfix hotfix/

remote名を変えたい場合:

git config --local kitflow.remote upstream

安全に使うためのポイント

  • 作業ツリーがdirtyな状態では、branch作成・finishなどの変更系コマンドは止まります。
  • --dry-runで実行予定のGitコマンドを確認できます。
  • --verboseでデバッグ用にGitコマンドを表示できます。
  • release / hotfix finishはannotated tagを作成します。既存tag名とは衝突できません。
  • merge conflictが起きた場合はGitの通常手順で解消してください。
kitflow --dry-run release finish 1.2.0
kitflow --verbose hotfix start 1.2.1
